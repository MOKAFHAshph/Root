# بنية BN Wallet System

## الهدف

المشروع بوت Telegram لإدارة محفظة USDT ومبيعاتها. يعتمد على SQLite و`python-telegram-bot`، ويحافظ على فصل واضح بين واجهة Telegram، منطق الأعمال، مزودي الخدمات، والتخزين.

## مسار التحميل

`bot/app.py` يحمل الوحدات بترتيب ثابت لأن بعض الوظائف توسع معالجات سابقة. يحتفظ `bot/runtime.py` بمسجل توافق يشارك الرموز العامة بين الطبقات.

تُزامن المعالجات العامة النهائية مثل `on_callback` و`on_message` و`post_init`، بينما تبقى المساعدات الخاصة ذات البادئة `_` مرتبطة بالوحدة التي عرّفتها. هذا يمنع تصادم دوال خاصة متشابهة الاسم، وهو التصادم الذي كان يعطل CAPTCHA عند `/start`.

أي تطوير جديد يفضّل أن يستخدم Imports صريحة، مع إبقاء المسجل فقط للأجزاء التي تحتاج ترتيب الطبقات الحالي.

## الطبقات

### `bot/config.py`

- قراءة `.env`.
- الثوابت والمسارات.
- إعداد سجل دوّار.
- حجب الأسرار من السجلات.
- توفير الاعتمادات المشتركة لوحدات التوافق.

### `bot/database.py`

- إنشاء SQLite وتهيئة الجداول الأساسية.
- اتصالات بمهلة 30 ثانية، WAL، Busy Timeout، Foreign Keys.
- العملاء والأدمن والإعدادات والتدقيق والأمان.
- التصدير والاستعادة الأساسيان.

### `bot/services/registration_payment.py`

- سجل كل مستخدمي البوت.
- الاشتراك الإجباري.
- قنوات الاشتراك والإذاعة.
- تحليل حقول عملية جيب ومطابقة بيانات المرسل.

### `bot/services/registration_flow.py`

- `/start` للمستخدم الجديد.
- CAPTCHA الرقمية.
- حسابات PENDING.
- التقاط الإحالة وإكمالها بعد التفعيل.

### `bot/wallet/`

- `core.py`: مخطط المحفظة والإعدادات العامة.
- `deposits.py`: جلسات الإيداع وحجز المراجع والإضافة الذرية.
- `deposit_verification.py`: الاستعلام من جيب واستخراج البيانات والمراجعة.
- `withdrawals.py`: حجز السحب والإرسال والإكمال والإرجاع.
- `statistics.py`: الإحصائيات الأساسية.

### `bot/providers/`

- `jaib.py`: الاتصال بجيب والاستعلام عن رقم العملية.
- `binance.py` و`payouts.py`: معلومات الشبكات والسحب.
- `binance_wallet.py`: تنفيذ ومراقبة سحوبات المحفظة عبر Binance فقط.

### `bot/services/backup_automation.py`

- إعدادات النسخ.
- الجدولة.
- قناة Telegram مستقلة.
- تتبع الملفات والاحتفاظ.
- الاستعادة من القناة أو الرفع اليدوي.

### `bot/services/log_management.py`

- لوحة إدارة ملف السجل.
- القناة/المجموعة.
- المستوى وDebug.
- التدوير والتصفير الآمن على Windows.
- ربط تسجيل بدء وإيقاف التطبيق.

### `bot/services/pdf_reports.py` و`bot/webapp/`

- تقرير ReportLab العربي.
- API الإحصائيات والتحقق من Telegram `initData`.

## المعاملات المالية

كل تغيير رصيد مهم يجري داخل `BEGIN IMMEDIATE`:

- إضافة الإيداع وتسجيل Ledger.
- حجز السحب.
- إكمال السحب.
- إرجاع السحب.
- مكافأة الإحالة.

تمنع حالات النهاية والمعاملات الذرية تكرار الرصيد عند وصول تحديث مكرر أو انهيار العملية بين خطوتين.

## حالات الإيداع

```text
WAITING_REFERENCE
  ├─ lookup failed ───────────────> WAITING_REFERENCE
  ├─ invalid/debit/below minimum ─> REJECTED
  ├─ uncertain metadata ──────────> PAYMENT_REVIEW
  └─ verified ─> VERIFIED ─> COMPLETED
```

رقم العملية لا يُحجز إلا بعد أن يجد جيب العملية، ثم يحجز ذريًا قبل أي إضافة أو مراجعة.

## حالات السحب

```text
RESERVED -> PROCESSING -> SUBMITTED -> COMPLETED
                       └-> STATUS_UNKNOWN / MANUAL_REVIEW
RESERVED/PROCESSING/... -> FAILED_RELEASED
```

الحجز ينقل الرصيد من المتاح إلى المحجوز. الإكمال يخصم المحجوز نهائيًا، والفشل المؤكد يعيده للمتاح.

## النسخ الاحتياطي

`create_backup_file()` و`DB.import_snapshot()` هما نقطتا التنفيذ الأساسيتان. توسع الوحدات اللاحقة Payload تدريجيًا لتشمل جداولها، ولا تنشئ منطق استعادة موازٍ.

## قواعد التطوير

- لا تضف أسرارًا إلى المصدر.
- لا تستخدم `except Exception: pass` في مسارات الأعمال.
- كل عملية مالية يجب أن تكون ذرية وقابلة لإعادة التنفيذ بأمان.
- لا تعتمد على قيمة يكتبها المستخدم إذا كان مزود الدفع يستطيع إرجاع القيمة الأصلية.
- أضف اختبارًا غير متصل لكل مسار جديد ثم اختبر المزود الحقيقي في بيئة تجريبية.
