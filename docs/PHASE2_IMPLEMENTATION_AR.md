# تنفيذ المرحلة الثانية

يوثّق هذا الملف مواضع تنفيذ متطلبات المرحلة الثانية واختبارات قبولها.

## 1. السيولة العامة

- الخدمة المركزية: `bot/services/liquidity.py`.
- العرض في البوت: `bot/ui/wallet.py`.
- العرض في Mini App: `GET /api/bootstrap` و`GET /api/me/withdrawals/networks`.
- لوحة التحكم: `bot/admin/wallet.py` ولوحة إعدادات Mini App.
- لا يتضمن الرد العام اسم مزود الصرف أو حقل `provider`.
- تُخصم قيمة `public_liquidity_reserve_usdt` قبل العرض.
- عند تسعير السحب تُحسب رسوم الشبكة ضمن السيولة المطلوبة.

## 2. الحد الأقصى لكل عملية

- القيمة المركزية: `withdrawal_operation_limit_usdt`.
- مفتاح التشغيل: `withdrawal_operation_limit_enabled`.
- يُطبّق داخل `wallet_create_withdrawal` وQuote الـMini App، وليس في الواجهة فقط.
- يظهر للمستخدم في شاشة السحب إذا كان مفعلاً.

## 3. الدفع والإيداع

- توضيح أن جيب آلي وفوري في القائمة الرئيسية.
- زر طرق الدفع الأخرى يفتح `ADMIN_CONTACT`.
- تعرض شاشة الإيداع الرقم البديل واسم المستفيد المحدد في `JAIB_SECONDARY_BENEFICIARY_NAME`.
- سياسة الطرف الثالث وإخلاء المسؤولية موجودان في البوت والـMini App.

## 4. تجربة Mini App

- أزرار نسخ للهواتف والمراجع والعناوين ورابط الإحالة وTelegram ID.
- نافذة نتيجة كبيرة للنجاح والفشل والمراجعة.
- السعر معروض بصيغة `ريال = 1 USDT`.
- المستخدم الجديد أو غير المفعّل يشاهد Landing Page ويمكنه إرسال طلب تفعيل.

## 5. الإحالات

- تسجل الإحالة أولاً بحالة `PENDING`.
- لا تُصرف المكافأة إلا عند تفعيل العميل.
- التفعيل من البوت أو Mini App يستدعي الدالة المركزية نفسها.
- تحديث المحفظة وLedger وحالة الإحالة يتم في معاملة SQLite ذرية.
- إعادة التفعيل آمنة؛ لا يمكن صرف المكافأة مرتين.

## 6. اختبارات القبول

يشغّل الأمر التالي جميع اختبارات Offline:

```bash
python verify_project.py
```

تشمل الاختبارات الحد الأقصى، الوصول المحدود، تفعيل الإحالة من Mini App، منع تكرار المكافأة، عدم تسجيل جلسات الإيداع، سلامة Ledger، JavaScript، النسخ والاستعادة، وتقارير PDF.
